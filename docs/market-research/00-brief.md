## 產品

- Flutter 開發的 iOS / Android app,把手機變成放在儀表板上的速度 HUD。
- 目標用戶:Tesla Model 3 / Model Y 車主。這兩款車方向盤後面沒有儀表,車速只顯示在中控大螢幕上。
- 核心價值:開車時用餘光約 0.3 秒就能看到車速,不用轉頭看中控。另有 mirror mode:手機平放,畫面反射在擋風玻璃上,效果像 HUD。
- 兩種模式:行駛中是 drive(極簡,速度數字為主);停車時是 parked(較豐富的儀表)。
- 資料來源(以這裡為準。`PRODUCT.md` 寫的「Phase 2 用 Tesla Fleet API」已過時):
  - **主要:Tesla 原生 BLE**。直接從車讀速度、電量、續航、檔位、充電、胎壓。不經雲端、不需要 Tesla 帳號、零費用,但需要一次性配對金鑰。協定是社群逆向工程出來的,Tesla 更新韌體後可能失效。
  - **備援:手機 GPS**,只提供速度。
  - 可選:Tesla Fleet API(遠端用)。進階:OBD-II(之後才做)。
- 現況:GPS 版已完成;BLE 版還在可行性驗證階段。尚未上架。
- v1 不包含:超速警示和速限顯示(需要地圖資料,已延後)。
- 已知競品線索:DriveCluster(App Store id6762794279),同樣走 Tesla BLE。

## 研究目標

回答四個問題:這個產品在**美國**和**台灣**有沒有市場?用戶最痛的是什麼?我們憑什麼贏?該怎麼上市?

兩個市場一律分開分析,因為法規、車輛保有量、通路和價格敏感度都不同。

## 共同規則

這些規則優先於你從 `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` 等檔案繼承的一般規則(例如「先進 plan mode」「先問再做」)。

1. **研究方式**:用你的網路搜尋和網頁讀取工具做桌面研究,自己直接做。不要開 subagent 或 workflow。
2. **不要卡住**:不要進入 plan mode,不要停下來問使用者任何問題,也不要等待確認。遇到不確定的地方就自己做合理假設,寫進報告的「假設」段落,必要時在 `team-board.md` 留言,然後繼續做。
3. **只寫兩個地方**:你自己的輸出檔,以及 `team-board.md`(只能在檔尾追加)。不要改 repo 裡其他檔案,不要 git commit,不要寫 Obsidian vault。
4. **證據**:每個關鍵數字和主張都附來源(URL + 發布日期),並標明是「事實」「估計」還是「推論」。資料超過 2 年要註明。找不到就寫「找不到可靠資料」,絕對不要編造。
5. **語言**:繁體中文(台灣用語),專有名詞保留英文。
6. **篇幅**:精簡,以表格和條列為主。開頭放 5 行以內的「重點結論」。
7. **報告結構**:重點結論 → 美國 → 台灣 → 假設 → 待驗證問題(需要訪談真實車主才能確認的事)→ 來源。角色說明裡另有規定的,照角色說明。
8. **完成時**:檔案寫好後,回覆的最後一行只寫 `DONE: docs/market-research/<你的檔名>`。
9. 主持人之後可能會請你修改。照指示改完,一樣用 `DONE:` 那一行結尾。
